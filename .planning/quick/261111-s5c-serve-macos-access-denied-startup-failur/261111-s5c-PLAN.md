# Quick Task 261111-s5c: Serve macOS access-denied startup failures through error mode

<objective>
On macOS 27, when Claude Desktop launches the server without the right privacy permission, macOS silently refuses reads of OmniFocus's sandbox folders. Today the eager IPC sweep in `app_lifespan` runs outside the `try` that feeds `ErrorOperatorService`, so the `PermissionError` kills the process and the client only sees "Connection closed".

After this task: **no startup failure escapes error mode**, and a macOS privacy block is recognised explicitly and answered on every tool call with a message that teaches the user how to fix it. The OmniFocus database check stops telling the user the database is *missing* when macOS is really blocking it.

Purpose: the project principle is "the server stays alive no matter what, and errors teach the agent what to do". This turns a crash into a teaching error.

Output: modified lifespan, error-mode service, agent message templates, repository factory path checks, plus tests.
</objective>

## Design decisions (owner-visible)

- **DD-1: how "macOS blocked access" is recognised.**
  - A macOS privacy block is a `PermissionError` whose `errno` is `EPERM` ("Operation not permitted"). That is what the sandbox and TCC return, and it matches the observed `[Errno 1]`.
  - `EACCES` ("Permission denied", ordinary Unix permission bits) is **not** a macOS block. It still lands in error mode, with the generic text and no Full Disk Access advice.
  - Recognition happens **once**, at the error-mode boundary (`ErrorOperatorService` construction). It checks the exception itself and its explicit `__cause__` chain. The startup sites (sweep, the real Bridge's `mkdir`, database check) just let the `PermissionError` propagate unwrapped.
  - Why there: any present or future startup site is covered without a new exception type, and `bridge/real.py` stays untouched.
- **DD-2: the wrapper text.**
  - Every startup failure keeps the same lead-in, "OmniFocus Operator failed to start:". Agents and existing tests key off it.
  - For the macOS block, the teaching body replaces both `{error}` and the generic closing "Restart the server after fixing.". Step (e), "fully quit and reopen the client", is the precise version of that line. Keeping both would give two conflicting restart instructions.
  - The generic template moves **verbatim** out of `service.py` into `agent_messages/errors.py`, next to the new one. Today it is the only inline agent-facing message left in `ErrorOperatorService`, and both siblings should be reviewable side by side.
  - All other startup failures read exactly as today.
- **DD-3: the database check.**
  - `os.path.exists` (which swallows every `OSError` as "missing") is replaced by a **metadata-only** check.
    - "Does not exist" (`FileNotFoundError`, `NotADirectoryError`) → the existing missing-database message, byte-identical.
    - "Refused" (`PermissionError`) → propagates as itself.
  - No file contents are read at startup. That keeps the later "defer to first tool call" work honest, and on older macOS a data read is what triggers the prompt.
  - The same helper also guards the bridge-only `.ofocus` check in the same file, which has the identical flaw. **Flag:** this is the one addition beyond the two sites the brief named. Strike that line if unwanted.
- **DD-4: uvx path discovery.**
  - Read `UV` (exported by uv to every process it spawns; verified live, see context). Resolve symlinks, look for a sibling `uvx`, and name its resolved real path.
  - Otherwise, tell the user to run `realpath "$(which uvx)"`.
  - **No** PATH-based `which uvx` fallback inside the server: with mise shims it resolves to the `mise` binary and would name the wrong program.
  - Discovery runs once, when error mode is entered for a macOS block. It never raises.
- **DD-5: the blocked path is named in step (a)**, taken from the exception's `filename` when present (the clause is dropped when absent). The generic wrapper carried it via `str(error)`, so it must not be lost.
- **Known limits (notes, not tasks):**
  - A contributor launching via `uv run` gets the `uvx` sibling named even though `uv` is the launcher there.
  - If macOS lets `stat` through but denies data reads on the database, the startup check passes and the denial surfaces at first read. That is covered by the separate, later deferral work.

## Message contract (macOS access-denied)

The executor may polish the wording but must keep this **order** and these **facts**. Steps (b) to (e) are written so the agent can relay them to the user.

> OmniFocus Operator failed to start: macOS is blocking this server from reading OmniFocus's data (blocked path: {path}).
>
> The user needs to fix this on their Mac. There are two ways:
>
> 1. If macOS shows a prompt asking whether "uvx" may access data from other apps, click Allow. macOS asks again every time the server launches.
> 2. To stop being asked, or if no prompt appears: open System Settings → Privacy & Security → Full Disk Access, click +, and add the program that launches this server: {fda_target} (in the file picker, press Cmd+Shift+G and paste the path).
>
> Granting Full Disk Access to Claude itself does not help: Claude Desktop launches MCP servers as their own responsible process, so macOS checks the launching program, not Claude.
>
> After either step, fully quit and reopen the MCP client (for example Claude Desktop) so the server starts again.

- `{fda_target}` when discovered: the resolved real path of `uvx`.
- `{fda_target}` otherwise: `uvx` plus the instruction to find its real path by running `realpath "$(which uvx)"` in Terminal.
- Order anchors that tests can use (suggested): "failed to start" < "macOS is blocking" < "Allow" < "Full Disk Access" < "Claude itself" < "quit".
- If ruff flags the arrow character, use the `→` escape, the same way `GET_PROJECT_INBOX_ERROR` escapes its em dash.
